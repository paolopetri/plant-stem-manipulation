# Later the same day — M1b: stem model `chain`

## Done
- Prototype (scratch) of the chain in PhysX: rigid capsule segments, D6 joints with locked translations (spherical joint, 3 DOFs `joint_<i>:0..2`), springs as Isaac Lab implicit actuators (E I / l, damping time x stiffness). Mass and stiffness arrive exactly; no stretch (strain 1.5e-6).
- Finding: PhysX solves the joint springs iteratively. Without armature the stem is far too soft (sag, hand value 14.17 mm):

  | Step x iterations, no armature | Sag |
  |---|---|
  | 2 ms x 8 | 228 mm, stem falls over |
  | 2 ms x 32 | 225 mm |
  | 2 ms x 128 | 62 mm |
  | 0.5 ms x 32 | 61 mm |

  Revolute joints (one bending axis) behave the same, so the spherical joint is not the cause.
- Joint armature fixes it (sag 32.6 / 16.2 / 14.3 mm for 1e-6 / 1e-5 / 1e-4 kg m²). Exact linear chain model (numpy, scratch) without gravity:

  | Armature [kg m²] | Mode 1 | Mode 2 | Mode 3 | Highest mode |
  |---|---|---|---|---|
  | 0 | 5.21 Hz | 32.7 Hz | 91.5 Hz | 3643 Hz |
  | 3e-5 | 5.19 | 29.2 | 53.1 | 65 |
  | 1e-4 | 5.15 | 24.1 | 33.2 | 36 |

  Static shapes do not depend on armature. With gravity (upright): mode 1 5.109 Hz (5.055 with 1e-4), push 0.05 N 9.44 mm.
- Time step, armature 1e-4, 8 iterations (push expected 9.44 mm, sag 14.17 mm):

  | Step | Push | Sag | Frequency | Damping ratio |
  |---|---|---|---|---|
  | 2 ms | 9.60 mm (+1.7 %) | 14.30 mm (+0.9 %) | 5.00 Hz | 0.056 |
  | 5 ms | 9.90 mm (+4.9 %) | 14.26 mm | 4.92 Hz | 0.063 |
  | 10 ms | 10.55 mm (+12 %) | 13.53 mm (-4.5 %) | 4.76 Hz | 0.072 |

- 512 envs x 2 stems (1024 stems, up to ~16 m from the origin): identical results in all envs, 3.16 ms per 2 ms step, i.e. about 15.8 ms per 10 ms simulated (rough: includes Python overhead; cable: 8.6 ms at cost 80).
- Stem model `chain` in the repo: `assets/stem/chain/chain.yaml` (20 segments, armature 1e-4, 2 ms, 8 / 1 iterations), `src/stem_manip/assets/stem/chain.py` (USD written from the yaml at spawn time into `assets/stem/chain/build/`, gitignored, file name = hash of the geometry values). Both model modules provide `segment_poses`, `segment_masses`, `joint_gains`, `write_kick`, `segment_force_setter`; `check_stem.py` uses only these (scene built after the app launch, run times in seconds, `--slow_motion`). The kick is now the same for both models: everything above the first joint rotates rigidly, the last segment's centre starts with 1 m/s.
- `check_stem.py --stem_model chain`: all 14 checks pass (mass 20.106 g, push 9.6 mm, sag 14.3 mm, 5.0 Hz, damping ratio 0.056, springs back 0.002 mm). `--stem_model cable`: all 13 pass (same values as before; kick peak 33.6 mm with the new kick instead of 32.3 mm).
- Joint reaction forces of the chain (`root_view.get_link_incoming_joint_force()`, joint frame x = stem axis): at rest the axial force equals the weight above each joint (0.1874 / 0.0986 / 0.0099 N at joints 1 / 10 / 19); with a 1 N pull on the tip -0.8126 / -0.9014 / -0.9901 N; a 0.01 N m twist on the tip gives -0.01000 N m twist torque at joint 1.

## Decisions
- `chain` defaults: armature 1e-4, 2 ms step (user agreed to the priority: chain in the repo first, then the write-up).
- The chain USD holds only the geometry; stiffness, damping, armature and masses are set at runtime, so randomizing them needs no USD rebuild (user: randomization must not become a bottleneck).
- No stretch spring in the chain on purpose: a real stem practically does not stretch (with E = 5e8 Pa, 1 N stretches the 0.4 m stem by 0.016 mm). The tensile damage limit uses the joint axial force instead of a strain.

- Write-up for the supervisors: `docs/stem_model_comparison.tex` (standalone LaTeX, follows `docs/stem_model_tradeoff.tex`; numbers as in this note; not compiled, no LaTeX installed). Slide deck for the meeting on 2026-10-06 as a claude.ai artifact (not in the repo).
- Kit viewer (`--viz kit`), three problems: (1) the first starts hung without output for minutes (window "not responding"); after one longer run Kit starts in about 4 s (likely a one-time shader cache, not confirmed). (2) The viewport was black: the scene had no light, and Kit's RTX renderer needs one (the Newton viewer does not); `check_stem.py` now adds a dome light (intensity 3000, as in Isaac Lab's tasks). Checked with a screenshot of the Kit window: ground, upright and horizontal stems visible. (3) "Base USD files have been changed, please fetch changes": the chain spawner rewrote the USD for the second stem while Kit had it open; it now writes the file only when its content changes. Also, `check_stem.py` rendered after every physics step (2 ms for the chain), far slower than real time; it now renders 30 frames per simulated second and paces them (`--slow_motion` works). A chain run with the Kit viewer takes 22 s, all checks pass.
- The warnings `[omni.physx.tensors.plugin] Failed to find rigid body at '...'` (183 per chain check, headless too) come from Isaac Lab itself: `PhysxManager` creates a rigid-body view over all prims (`create_rigid_body_view("/**")`, `isaaclab_physx/physics/physx_manager.py`) for the visualizers, and PhysX warns for every prim that is not a rigid body (joints, collision shapes, render prims). Harmless; all checks pass with them.

# Later the same day — M1b: contact test (prototype) and smooth stem surface

## Done
- Contact test prototype (scratch, not in the repo yet): FR3 + `fork_v2` pushes the `chain` stem in PhysX, robot driven by differential IK on `fork_v2` + `tool_tip_offset`, stem moved only by contact; contact force from Isaac Lab's `ContactSensor` on the stem segments, filtered to the fork, compared with the force from the stem's stiffness (linear chain, bending only, no gravity) and from the base-joint moment / lever. Push at 0.3 m height, 5 cm/s, 2 ms step, PhysX default contact settings.
- Fork collision shape: the robot asset approximates every collision mesh by its convex hull, which fills the fork's slot (8 mm wide at the bottom, 19 mm at the prong tips, 150 mm long). Contact onset in the slot test: hull 173 mm early (at the prong tips), PhysX's default convex decomposition 112 mm early, a fine decomposition (64 hulls, voxel resolution 2e6, error 1 %, shrink wrap) 1.5 mm early (stem reaches the slot bottom).
- Setup findings: robot gravity off is needed for the IK to track (with gravity: about 4 cm sag, kept as a steady error by differential IK + stiff PD); approach along +y instead of +x (joint 4 at its limit near the base); the default joint pose must be written explicitly (`sim.reset()` leaves the FR3 at zero, singular, joints 4 and 6 at their limits); Isaac Lab reports the FR3 as floating base (`is_fixed_base` False, Jacobian with 6 base columns, fork = body 8, joints = columns 6-12) although converted with `--fix-base`.
- Smooth stem surface (`feat/smooth-stem-collision`): the chain's capsules only touched at the joints, leaving a groove of 4 mm depth every 2 cm (also on the straight stem). Now each capsule's cylinder part is the segment length, so the round ends are centred on the joints and neighbours share the same sphere: a smooth tube at any bend; end segments shortened by half a radius (tube from the base to the tip). `check_stem.py --stem_model chain`: all values unchanged. Close-up screenshot of a strongly bent stem in the Kit viewer: smooth tube.
- Contact tests, fine fork decomposition, beaded vs. smooth stem:

  | Test | Beaded stem | Smooth stem |
  |---|---|---|
  | Slot 5 cm: force sensor / stiffness / base moment | 0.61 / 0.65 / 0.66 N | 0.65 / 0.65 / 0.66 N |
  | Side 5 cm: force sensor / stiffness / base moment | 0.64 / 0.65 / 0.67 N | 0.63 / 0.65 / 0.67 N |
  | Slot 15 cm: maximum contact force | 32 N (stem dragged along while pulling back) | 1.7 N |
  | Slot 15 cm: maximum curvature | 8.7 1/m | 4.7 1/m |
  | Slot 15 cm: contact with the arm | link 6 2.8 N, link 5 1.2 N | link 5 0.05 N |

  The jam on retract came from the grooves catching the slot edges (not from wedging in the tapered slot, as first assumed). Far push: sensor 1.02 N along the push vs. 1.61 / 1.62 N from stiffness / moment; at 130 mm deflection the linear reference does not apply and the stem slides along the slot (reported only).

## Decisions
- Smooth collision tube for the chain (user): a convex hull around all segments is not possible (one collider per rigid body; it would also fill the inside of a bend), overlapping capsules give the same smooth surface.
- Fork collision: fine convex decomposition, added to the asset pipeline (next step).
- Robot gravity off (user), as Isaac Lab's high-PD Franka for task-space control; on the real robot Franka compensates gravity, with the fork's measured mass entered as end-effector load.
- Fork collision in the asset pipeline (`feat/fork-convex-decomposition`): `fork_v2.yaml` has a new optional section `collision_approximation` (convex decomposition, 64 hulls, voxel resolution 2e6, error 1 %, shrink wrap); `assets/fr3/set_collision.py` writes it onto the end-effector's collision mesh in the converted USD, `convert_to_usd.sh` runs it after the converter. Found while doing it: the converter does not overwrite an existing output and silently writes to `fr3_<ee>_1/` instead, so rebuilds never updated the asset; `convert_to_usd.sh` now removes the old output first. Clean rebuild: the only text change in the USD is the fork's collision setting; `check_fr3.py` passes; the slot contact test with the built asset gives the same result as the scratch copy (contact at the slot bottom, 0.65 / 0.65 / 0.66 N).
- Robot gravity off (`feat/robot-gravity-off`): `fr3_cfg` sets `disable_gravity=True` on the robot's rigid bodies only (as Isaac Lab's `FRANKA_PANDA_HIGH_PD_CFG` for task-space control). Checked in the libfranka docs: torque commands are sent "without gravity and friction" (the robot compensates both), position / Cartesian commands go through the internal joint impedance controller, and the tool is included via `setLoad` (load mass, flange-to-CoM translation, inertia) or a Desk end-effector profile. `check_fr3.py`: start pose held exactly (0.000 rad, was 0.055 rad). Contact test without override: start error 0.03 mm, same forces; the stem keeps its gravity (axial force at joint 1 before contact 0.1874 N = weight above). Gravity question removed from docs/TODO.md; the load setting added to the "weigh the forks" item.
- Contact check in the repo (`feat/contact-check`): `scripts/check_contact.py --test slot|side|slot_far` (from the prototype; tool-tip path with differential IK, `ContactSensor` filtered to the fork and to the arm links); `stem_reference.chain_point_compliance` (deflection per force at a height, bending only) with two unit tests (matches `chain_push_deflection` on the last segment; approaches h³/(3EI)); `chain.joint_wrenches` (force and moment through each joint, joint frame).
